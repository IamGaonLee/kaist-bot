# 0단계 기술 검증 지시문 (Claude Code용)

이 파일과 `kaist-agent-design.md`를 새 프로젝트 폴더의 `docs/`에 넣고, Claude Code에 "docs/phase0-instructions.md를 읽고 0단계를 진행해줘"라고 시키면 된다.

---

## 배경

`docs/kaist-agent-design.md`는 KAIST KLMS를 수집하는 개인용 TypeScript CLI의 설계 문서다. 설계 11절의 가정 A1~A7은 아직 검증되지 않았다. 이번 작업의 목표는 **가정을 검증하고 보고서를 쓰는 것**이며, CLI 본체 구현은 하지 않는다.

## 반드시 지킬 규칙

1. **읽기만 한다.** KLMS에서 제출, 글쓰기, 설정 변경 등 상태를 바꾸는 요청을 보내지 않는다.
2. **비밀번호를 다루지 않는다.** 로그인은 사용자가 브라우저 창에 직접 입력한다. 비밀번호를 대화에 적어달라고 요청하거나, 파일이나 코드에 저장하지 않는다.
3. **2단계 인증을 우회하려 하지 않는다.** 사용자가 폰에서 승인할 때까지 기다린다.
4. **요청은 천천히 보낸다.** 페이지 요청 사이에 1초 이상 간격을 두고, 같은 페이지를 반복해서 긁지 않는다. 검증에 필요한 최소한만 접속한다.
5. **개인정보를 저장소에 넣지 않는다.** 쿠키, 브라우저 프로필, 저장한 HTML 샘플은 `.gitignore`에 등록된 `local/` 폴더에만 둔다. 보고서에는 이름, 학번, 성적 등을 적지 않는다.
6. **불명확하면 추측하지 말고 사용자에게 묻는다.** 질문은 한 번에 하나씩, 왜 묻는지 설명과 함께 한다.
7. 사용자의 로그인이나 폰 승인이 필요한 순간에는 무엇을 해야 하는지 분명히 알린 뒤 기다린다.

## 준비

- Node.js 프로젝트 초기화 (TypeScript, Playwright)
- `npx playwright install chromium`
- `local/` 폴더 생성 및 `.gitignore` 등록
- 검증용 스크립트는 `scripts/phase0/`에 둔다. 버려도 되는 코드이므로 구조에 공들이지 않는다.

## 검증 항목

### V1. 자동화 브라우저 로그인 (가정 A2)

- Playwright의 persistent context(프로필 경로: `local/profile/`)로 창이 보이는 Chromium을 띄우고 `https://klms.kaist.ac.kr`로 이동한다.
- 사용자가 SSO 로그인과 폰 승인을 마칠 때까지 기다린 뒤, 로그인된 KLMS 화면에 도달했는지 확인한다.
- 기록할 것: 로그인이 막히거나 추가 확인(캡차, 차단 문구)이 뜨는지, 거쳐 간 URL 순서, 로그인 완료를 판별할 수 있는 신호(URL, 쿠키 이름, 페이지 요소).
- 막힌다면: 사용자의 일반 Chrome에 연결하는 방식(`channel: 'chrome'` 또는 CDP 연결)으로 다시 시도하고 결과를 비교한다.

### V2. 세션 재사용과 유지 시간 (가정 A3)

- 로그인 직후 쿠키 목록을 확인한다. 각 쿠키가 세션 쿠키인지 만료 시각이 있는지 기록한다(값은 기록하지 않는다).
- 브라우저를 닫고 같은 프로필로 다시 열어 로그인 상태가 유지되는지 확인한다.
- 간단한 확인 스크립트를 만들어, 사용자가 원할 때 실행하면 세션이 아직 유효한지 알려주게 한다. 로그인 후 30분, 2시간, 다음 날에 실행해 보도록 사용자에게 안내하고 결과를 보고서에 추가한다.
- 기록할 것: 창을 닫으면 풀리는지, 대략 얼마나 유지되는지, 만료 시 어떤 응답이 오는지(리다이렉트 URL 등 만료 감지 방법).

### V3. 브라우저 없이 요청 가능한지 (가정 A1)

- V1에서 얻은 쿠키를 써서 브라우저가 아닌 일반 HTTP 요청(Node fetch)으로 KLMS 대시보드를 가져와 본다.
- 로그인된 내용이 오는지, 로그인 페이지로 튕기는지 확인한다.
- 된다면 수집은 가벼운 HTTP 요청으로, 안 된다면 수집 전체를 Playwright로 해야 한다. 이 결론을 명확히 적는다.

### V4. Moodle API 사용 가능 여부 (가정 A7)

화면 긁기보다 API가 훨씬 안정적이므로 꼼꼼히 확인한다.

- **V4-a. 모바일 웹서비스**: `/lib/ajax/service-nologin.php`로 `tool_mobile_get_public_config`를 호출해 모바일 서비스가 켜져 있는지 본다. 켜져 있으면 로그인된 세션으로 `/admin/tool/mobile/launch.php?service=moodle_mobile_app&passport=<임의값>`에 접속해 토큰이 발급되는지 확인한다. 사용자 설정 메뉴에 "보안 키" 항목이 있는지도 본다.
- **V4-b. 세션 기반 AJAX API**: 페이지 소스에서 `sesskey`를 찾아 `/lib/ajax/service.php?sesskey=...`로 다음 함수들을 호출해 본다.
  - `core_course_get_enrolled_courses_by_timeline_classification` (수강 과목)
  - `core_calendar_get_action_events_by_timesort` (다가오는 마감)
- 기록할 것: 각 방법의 성공 여부, 응답에 들어 있는 필드(과목 ID, 과제 ID, 마감 시각 형식 등).
- Moodle 버전을 알 수 있으면 함께 적는다.

### V5. 페이지 구조 조사 (가정 A4, A5)

수강 과목 중 하나를 골라(어느 과목으로 할지 사용자에게 묻는다) 다음을 조사한다.

- 수강 과목 목록과 학기 구분을 어디서 얻는지
- 과목 페이지의 주차/섹션 구성
- 활동 유형별 식별 방법과 URL 형식: 파일, 폴더, 과제, 퀴즈, 게시판/공지, 영상, 외부 링크
- 파일 다운로드 링크 형식(`pluginfile.php` 등)과, 쿠키만으로 직접 받을 수 있는지 (작은 파일 하나로만 시험)
- 과제 페이지에서 설명문, 마감 시각, 첨부파일, 제출 상태가 있는 위치
- 공지/게시판 글 목록과 본문의 위치
- 영상이 어떤 방식으로 제공되는지(다운로드 가능 파일인지, 스트리밍 플레이어인지). **영상은 내려받지 않는다.** 제목과 링크를 얻을 수 있는지만 확인한다.
- 각 항목의 고유 ID(증분 수집에 쓸 것)와 수정 시각을 알 수 있는지

HTML 샘플은 `local/samples/`에 저장한다. KLMS가 표준 Moodle과 다르게 커스터마이징한 부분이 보이면 따로 적는다.

### V6. 이용 규정 확인 (가정 A6)

- KLMS 이용 약관, KAIST 정보보호 관련 규정에서 자동화 도구, 크롤링, 계정 사용에 관한 조항을 찾아본다(웹 검색과 로그인 후 보이는 약관 페이지).
- 본인 계정으로 본인이 수강하는 과목의 자료를 개인 용도로 수집하는 것이 문제 되는지 판단 근거를 적는다. 명확한 조항이 없으면 "명시 조항 없음"으로 적고 추정하지 않는다.
- 강의자료의 재배포 금지 등 저장한 자료의 취급과 관련된 조항도 확인한다.

## 산출물

`docs/phase0-report.md`를 작성한다. 형식:

1. **요약**: 가정 A1~A7 각각에 대해 "성립 / 불성립 / 부분 성립 / 확인 불가" 한 줄 판정
2. **항목별 상세**: V1~V6의 관찰 내용과 근거
3. **설계 변경 제안**: 검증 결과에 따라 설계 문서에서 바꿔야 할 부분. 특히 다음을 명시한다.
   - 수집 방식: API(V4) / HTTP 요청 + HTML 파싱 / 전부 브라우저 자동화 중 어느 것으로 갈지
   - 세션 만료 감지 방법
   - 로그인 완료 판별 방법
4. **확인하지 못한 것과 이유**
5. **사용자에게 물어볼 것**

보고서는 관찰한 사실과 추정을 구분해서 쓴다. 잘 안 된 부분을 축소하지 않는다.

## 끝나면

보고서를 사용자에게 보여주고 멈춘다. 설계 문서 수정과 1단계 구현은 사용자가 보고서를 검토한 뒤에 진행한다.
