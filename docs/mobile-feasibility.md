# 모바일(iOS·Android) 구현 가능성 검토

작성 2026-10-16. 사용자 질문 "같은 프로그램을 모바일로도 구현 가능한가?"에 대한 조사 결과. 결정은 사용자가 한다.

## 결론 요약

- **가능하지만 "같은 프로그램"을 옮기는 게 아니라 절반은 새로 만드는 일**이다. 코어(`src/`, 59파일)의 파싱·일정·검사 로직은 재사용되지만, 로그인·저장·AI·드라이브·백그라운드 실행은 모바일에서 전부 다른 방식이 필요하다.
- 지금 구조로도 **폰에서 보는 것**은 이미 된다: 자료는 구글 드라이브 앱, 일정은 구글 캘린더 앱. 부족한 것은 폰에서 (1) 동기화를 시작하는 것, (2) AI에게 묻는 것, (3) 일정 제안을 승인하는 것 세 가지.
- 권고: **지금은 만들지 않는다.** 위 세 가지가 꼭 필요하면 "PC 앱에 작은 원격 조작 창구"(아래 대안 B)가 모바일 앱보다 10배 싸다. 모바일 앱은 지인 배포가 안정된 뒤, 수요가 확인되면 Capacitor 방식(대안 A)으로.

## 코어가 모바일에서 그대로 도는가

| 구성 | 현재 구현 | 모바일에서 | 재사용 |
|---|---|---|---|
| KLMS·포털 파싱 (`src/klms`, `src/sites`) | fetch + cheerio | 그대로 동작(순수 JS) | O |
| 일정 추출·검사 (`src/events`) | 순수 TS | 그대로 | O |
| 저장소 (`src/store/db.ts`) | **`node:sqlite`**(Node 22+ 내장) | 없음. Capacitor SQLite / expo-sqlite / op-sqlite로 교체 필요. 쿼리 문자열은 재사용 | △ |
| 파일 시스템 | `node:fs` 16개 파일 | 앱 샌드박스 FS API로 교체 | △ |
| 로그인 (`src/sso`) | 숨긴 브라우저(Playwright/Electron)에서 아이디 채움·버튼 클릭·쿠키 추출 | **WebView**로 같은 흐름 가능(아이디만 채우고, 사용자가 폰에서 승인 → 같은 폰이라 오히려 자연스러움). 단 iOS WKWebView 쿠키 추출·headless 동작은 별도 구현 | △ |
| 드라이브 저장 (`src/files`) | 로컬 동기화 폴더에 파일 복사 | 폰에는 동기화 폴더가 없음 → **Google Drive API 업로드**로 교체. PDF 생성(`printToPDF`)도 다른 방법 | X |
| 구글 캘린더·Gmail (`src/google`) | REST + 로컬 OAuth 리디렉션 서버 | REST는 그대로, OAuth는 모바일 흐름(PKCE·앱 스킴)으로 교체 | △ |
| 로컬 AI (`src/ai/local.ts`) | node-llama-cpp(Vulkan) | 없음. llama.cpp 모바일 바인딩(llama.rn 등)이 있지만 3B 모델은 폰 RAM·발열 부담. **현실적으로 외부 API 키만** | X |
| 외부 AI (`src/ai/openai.ts`) | fetch | 그대로 | O |
| 자동 동기화 | Electron 상주 + 작업 스케줄러 | iOS는 백그라운드 실행 제한(15분 단위도 보장 안 됨), Android는 WorkManager로 가능하지만 세션 만료 시 폰 승인은 사용자가 앱을 열어야 함 | X |
| 배포 | GitHub 릴리스 exe | App Store $99/년 + 심사(학교 로그인 자동화 앱은 거절 위험), Android는 APK 직접 배포 가능 | X |

재사용 가능 비율(대략): 파서·일정·구글 REST ≈ 코어의 60%. 나머지 40%와 앱 껍데기(화면·WebView 로그인·저장·OAuth·푸시)는 새로 만든다.

## 선택지

### A. Capacitor(또는 React Native) 앱 — "진짜 모바일 앱"
- 지금 렌더러(HTML/JS)를 거의 그대로 화면으로 쓰고, 코어는 TS 그대로 번들. SQLite·FS·WebView 로그인·Drive API·OAuth만 플러그인으로.
- 장점: 폰 단독으로 동기화·질문·승인 가능. 로그인 승인이 같은 기기라 UX가 좋다.
- 단점: 위 표의 X·△ 항목 전부 구현. 로컬 AI 없음(외부 키 필수 → 비용). iOS 백그라운드 동기화 불가(앱을 열 때 동기화). 앱스토어 심사 위험. **예상 작업량: 데스크톱 앱 A~F 전체와 비슷하거나 그 이상(수 주).**

### B. PC 앱에 원격 조작 창구 — "폰은 리모컨"
- PC 앱이 켜져 있을 때 폰에서 동기화 시작·질문·일정 승인을 보내는 통로만 만든다. 방법 후보:
  1. **claude.ai/code 원격 제어**(이미 가능, 사용자 2026-10-15 결정): 폰 브라우저에서 PC의 Claude Code를 조작해 `kaist` CLI를 돌린다. 추가 개발 0.
  2. PC 앱이 구글 드라이브의 작은 "요청 파일"을 감시하고, 폰에서 드라이브 앱으로 그 파일을 고치면 실행(동기화·일정 승인). 개발 1~2일, 서버·네트워크 설정 없음. 단 질문-답변은 왕복이 느리다(드라이브 동기화 지연 수십 초).
  3. PC 앱에 로컬 웹 서버 + Tailscale 같은 사설망: 폰 브라우저로 지금 UI를 그대로 연다. 개발 2~3일이지만 사용자가 2026-10-15에 "웹 서버 방식 보류"로 결정한 항목.
- 단점: PC가 꺼져 있으면 아무것도 안 된다(지금과 동일).

### C. 지금 그대로 (추가 없음)
- 폰: 드라이브 앱(자료·요약 PDF) + 캘린더 앱(마감·시험·휴강). PC: 동기화·질문·승인.
- 부족한 것: 폰에서 질문·승인. 이게 얼마나 자주 필요한지 실사용으로 확인한 뒤 A/B를 고르는 게 낫다.

## 권고

C로 두고 실사용 → "폰에서 승인·질문이 꼭 필요하다"가 확인되면 B-2(드라이브 요청 파일) 또는 B-1(원격 제어) → 지인 여러 명이 폰 앱을 원할 때만 A.

## 근거 메모
- `src/store/db.ts`가 `node:sqlite`를 쓴다(Electron 44 = Node 24라 데스크톱은 그대로). 모바일 런타임에는 없다.
- `node:fs` 사용 파일 16/59: ai/context·models, config, events/extract, files/*, google/oauth, klms/session-store, sso/account, store/lock·queries·snapshots, sync/sync.
- 로그인 흐름(`docs/app-design.md` B·C2)은 "프로그램이 화면을 넘기고 사용자는 폰 승인만" — WebView로 옮기면 승인 기기와 앱 기기가 같아져 흐름 자체는 더 단순해진다. 다만 KAIST 정보보안지침(비밀번호 자동입력 금지)은 그대로 지켜야 한다.
- 로컬 AI 모델(Qwen2.5-3B Q4, 2GB)은 폰에서 돌릴 수는 있어도 답 하나에 수십 초·발열. 지인 배포용으로는 외부 키가 현실적.
